# AFF SAINTS CRM

Внутренняя CRM для команды affiliate-маркетинга: учёт связок (оффер + подход + креатив + ГЕО + байер),
бюджетов, результатов (CR / ROI / ROAS / profit), истории решений и комментариев команды.

Стек: **Next.js 16.4.3** (App Router, Cache Components) · **React 19.3.0** · **TypeScript (strict)** ·
**PostgreSQL** · **Prisma 7.10.1** + `@prisma/adapter-pg` · **shadcn/ui (radix)** + Tailwind CSS v4 ·
**NextAuth v5** (credentials, JWT-сессии) · **Zod 4** + React Hook Form · **TanStack Table** ·
**React Query** · **Recharts** · **react-hot-toast**.

Prisma закреплена минором `7.10.1`, а не `latest`: `npm i prisma` отдаёт CLI `8.0.0-rc.29` при клиенте 7.x —
рассинхрон мажоров ломает генерацию клиента.

## Требования

- Node.js 20+ (проверено на 24)
- PostgreSQL 15+ (проверено на 18)

## Установка

```bash
npm install
copy .env.example .env       # Linux/macOS: cp .env.example .env
npm run db:migrate           # создаёт БД (если её нет), применяет миграции, генерит клиент
```

и порты настраиваются через переменные):

Этап 6 проверяет уже не «эндпоинт отвечает 200», а согласованность: сумма трат по байерам и
сумма дохода по офферам сходятся с итогами периода (допущение — копейки на округлении), ROI
команды равен отношению дохода к трате, а не среднему по связкам, первая ступень воронки равна
счётчику активных связок, явный диапазон считается включительно (`from` + 7 дней → 8 дней), а
ранжирование отсекает связки без трат и переворачивается по `order=asc`. Справочники: чтение
открыто байеру, запись — только админу, дубликат имени и email → 409, пустой PATCH → 422,
частичный PATCH меняет ровно присланное поле (та же проверка, что спасла `PUT /api/bundles/[id]`
от `.default()` в `.partial()`), удаление оффера, который ещё ведут связки, отказывает и
предлагает деактивацию, удаление ГЕО возвращает число снятых меток, отключённый аккаунт не может
начать сессию, а включённый — снова может. Отдельно проверяется инвалидация: созданное,
переименованное и деактивированное значение справочника должно появиться (или исчезнуть) в
отрендеренном `/bundles` сразу, без ожидания жизни кэша.

Этап 7 проверяет три новые вещи и то, что они не расходятся с уже сделанным. Импорт: анониму
401, шаблон отдаётся файлом, `dryRun` **не пишет** (строка «в превью ок, в списке — нет»),
неизвестный оффер валит строку сообщением про Settings, «конверсий больше, чем кликов» ловится
схемой формы, колонки `CR %`/`ROI %`/`Profit` читаются и отбрасываются с отчётом в
`columns.ignored`, байер не может импортнуть на чужое имя, `skipInvalid: false` отказывает всему
файлу, 501 строка — 413, а заголовок без обязательных колонок — 422 со списком, каких не хватает.
Уведомления: алерт поднимается на записи (импортированная связка с ROI −80% при пороге −20%),
его видят владелец и админы и не видит чужой байер, отметка по id и «прочитать всё» считаются
точно, смещение порога до −90 очищает колокольчик, возврат к −20 поднимает алерт заново, а
удаление связки уносит её алерты каскадом. Журнал: 401 анониму, 403 байеру, сортировка по
времени, `pageSize`, фильтр по человеку/полю/типу, поиск по названию связки, 422 на неизвестный
тип и отсечение страницы; отдельно — что импорт оставил в журнале собственное событие `import`,
и что `?field=budgetSpent` не возвращает комментарии. Страницы: `/audit` рендерится таблицей для
админа и объяснением для байера, анонима редиректит с `?from=%2Faudit`, колокольчик присутствует
в шелле.

Смоук **самочистящийся**: связка, созданная в блоке этапа 4–5, в конце удаляется (комментарии и
история каскадом), два зарегистрированных аккаунта удаляются блоком этапа 6, аккаунт импорта и
две импортированные связки — блоком этапа 7, а все правки сидовых строк (имя байера, флаг
доступности, порог алертов, ГЕО временной связки) возвращаются на место — поэтому счётчики и
список команды не ползут от прогона к прогону.

## API

Все эндпоинты требуют сессию (кроме `POST /api/auth/register`), отвечают `{ data }` или
`{ error: { message, fields } }` и проверяют права через `lib/dal.ts`.

| Метод | Путь | Назначение |
| ----- | ---- | ---------- |
| `POST` | `/api/auth/register` | регистрация (всегда роль `USER`) |
| `GET/POST` | `/api/auth/[...nextauth]` | NextAuth: csrf, callback, session |
| `GET` | `/api/bundles` | список: `search`, `status` (csv), `offerId`, `userId`, `mine`, `geoId`, `tagId`, `roiMin`, `roiMax`, `dateFrom`, `dateTo`, `sort`, `order`, `page`, `pageSize`, `archived` |
| `POST` | `/api/bundles` | создание связки |
| `GET` | `/api/bundles/[id]` | детальная карточка: история, комментарии, дневные метрики, права текущего зрителя |
| `PUT` | `/api/bundles/[id]` | частичное обновление: присылаются только изменённые поля, на каждое пишется запись в историю |
| `DELETE` | `/api/bundles/[id]` | удаление (только админ); не-destructive альтернатива — архив |
| `GET` | `/api/bundles/export` | тот же фильтр, CSV-файл вместо страницы |
| `POST` | `/api/bundles/import` | импорт CSV: `file` в multipart или `{ text }` в JSON; `dryRun` (по умолчанию `true`), `skipInvalid` |
| `GET` | `/api/bundles/import/template` | шаблон колонок одним файлом |
| `POST` | `/api/bundles/bulk` | массово: `status` \| `archive` \| `unarchive` \| `delete` |
| `PATCH` | `/api/bundles/[id]/status` | смена статуса одной связки |
| `POST` | `/api/bundles/[id]/comments` | комментарий в тред связки (может любой член команды) |
| `GET` | `/api/notifications` | свои алерты + счётчик непрочитанного; `unread=1` — только новые |
| `POST` | `/api/notifications/read` | отметить прочитанным: `{ ids }` или пустое тело = все непрочитанные |
| `DELETE` | `/api/notifications/[id]` | убрать уведомление из колокольчика |
| `GET` | `/api/audit` | журнал изменений по всей системе — **только админ**: `actorId`, `field`, `kind`, `bundleId`, `search`, `dateFrom`, `dateTo`, `order`, `page`, `pageSize` |
| `GET` | `/api/analytics/dashboard` | итоги периода, сравнение с предыдущим, воронка статусов |
| `GET` | `/api/analytics/by-buyer` | прибыль по байерам за период |
| `GET` | `/api/analytics/by-offer` | трата против дохода по офферам за период |
| `GET` | `/api/analytics/top-bundles` | связки, ранжированные по ROI периода (`order=asc` — худшие) |
| `GET/POST` | `/api/offers` | список офферов / создать (создать — только админ) |
| `PUT/DELETE` | `/api/offers/[id]` | частичное обновление / удалить (пока не используется связками) |
| `GET/POST` | `/api/geos` | список ГЕО / создать |
| `PUT/DELETE` | `/api/geos/[id]` | обновление / удаление со снятием метки со связок |
| `GET/POST` | `/api/tags` | список тегов / создать |
| `PUT/DELETE` | `/api/tags/[id]` | обновление / удаление со снятием метки со связок |
| `GET` | `/api/users` | аккаунты с ролями и правами — **только админ** |
| `PUT/DELETE` | `/api/users/[id]` | имя / email / роль / доступность; удаление — если аккаунт ничего не ведёт |
| `GET/PUT` | `/api/settings` | порог ROI-алертов: читают все, пишет админ |

Форма создания/редактирования — модалка на React Hook Form + той же Zod-схеме, что и на сервере;
CR, ROI, ROAS и прибыль считаются на лету по мере ввода чисел. Байер создаёт связку всегда на
себя, переназначить байера и удалить чужую связку может только админ.

Про `PUT` и Zod: `.partial()` в zod 4 **сохраняет `.default()`** поля. Если собирать partial из схемы
с дефолтами, то `{}` пройдёт валидацию и превратится в полный payload — PUT, который хотел поменять
одну колонку, молча обнулил бы остальные. Поэтому общие поля объявлены без дефолтов, дефолты
добавляются только в create-схему через `.extend()`, а partial строится на чистых полях.

`sort` принимает только белый список колонок. `roi`, `cr` и `profit` — производные, их нельзя
ни отсортировать, ни отфильтровать через `orderBy` в Prisma, поэтому для таких запросов
сначала читаются лёгкие строки (только числа), считаются в `lib/bundles.ts`, и только
получившаяся страница поднимается вместе со связями. Окно скана ограничено
(`DERIVED_SCAN_LIMIT`), и при переполнении в ответе приходит `truncated: true` — экран
показывает это предупреждение вместо молча неверного порядка.

## Детальная страница и лента изменений

`/bundles/[id]` — серверный рендер: один `findUnique` за связкой, историей, комментариями
и дневными метриками. Ссылка на связку работает сама по себе (расшаренный URL, refresh,
«назад»), а имя в списке и в топ-5 на главной теперь кликабельны.

- **Страница намеренно не кэшируется.** Кэш по id либо показал бы старую ленту сразу после
  комментария, либо потребовал бы отдельный тег на каждую связку; вместо этого мутации зовут
  `router.refresh()`, и сегмент перечитывается из БД. Граница стрима — `loading.tsx` сегмента.
- **Лента = `BundleChange` + `Comment`, слитые по времени** (от старых к новым), как тред в
  GitHub issues. Комментарий не пишется дублем в `bundle_changes`: строка в одном месте не
  разъедется с тредом, из которого она взята.
- **`field` — машинный ключ, а не подпись.** Сид, форма правки и bulk-действия пишут одни и те
  же имена (`status`, `budgetPlanned`, `isArchived`, `bundle`), значения остаются как лежат
  (enum-ключ, число строкой). Слова подбирает `lib/timeline.ts` при рендере: деньги форматируются
  валютой, статусы — эмодзи и меткой, а неизвестный ключ показывается своим именем, чтобы поле,
  добавленное позже, не исчезло из истории.
- **Права считаются на сервере от смотрящего** (`permissions.canManage` / `canDelete`) и едут в
  DTO только затем, чтобы понять, какие кнопки рисовать; каждый write-эндпоинт проверяет те же
  правила заново.
- **Комментарий не трогает `Bundle.updatedAt`** — иначе колонка «Updated» во списке врала бы о
  том, когда в последний раз двигались цифры.
- **Грабли PPR на динамическом маршруте:** `usePathname()` в `MobileNav` ломал пререндер
  `/bundles/[id]` (`CLIENT_HOOK_DYNAMIC`) — на `/bundles` путь известен ещё на билде, на
  маршруте с параметром нет. Поэтому у `MobileNav`, как у `Sidebar` и `Header`, теперь свой
  `<Suspense>`.

## Аналитика

`/analytics` — четыре отдельных запроса (`/api/analytics/*`) поверх одного периода, а не один
серверный рендер: период живёт в URL и принадлежит клиенту, поэтому смена окна не гоняет страницу
через сервер, а каждая карточка показывает свой скелетон.

- **Считается по `BundleMetric`, а не по итогам на связке.** Вопрос «что было в этом окне» могут
  ответить только дневные строки; `bundle.budgetSpent` остаётся авторитетным для формы, поэтому
  одна и та же связка в таблице и на графике показывает разные числа — и это осознанно.
- **Границы окна — UTC-дни** по той же причине, что и `@db.Date` в схеме: локальная полночь на
  машине в UTC+4 сдвинула бы окно на день.
- **Архивные связки входят в итоги.** Их трата была реальной; исключить её означало бы нарисовать
  команде прибыль, которой не было.
- **ROI группы считается от сумм группы, а не как среднее по связкам**, иначе тест на $40 весил бы
  столько же, сколько тест на $4 000. Среднее по связкам показывается отдельной строкой
  («Mean per bundle») — это честный второй взгляд на те же данные, а не замена первому.
- **Воронка статусов не зависит от периода** и говорит об этом в подписи: статус — состояние, а не
  событие, и в дневных строках его нет. Окно на неё влиять не может.
- **Ранжирование обходит связки без трат** — ноль в знаменателе это не «ROI 0%», а «доказательств
  нет». Тот же запрос с `order=asc` отвечает на вопрос «что сливать», поэтому второго эндпоинта
  под это нет.

## Справочники

`/settings` — вкладки офферов, ГЕО, тегов, байеров и порог алертов. Чтение открыто всякому
вошедшему (без этих списков форма связки не рисуется), запись — только админу: строка справочника
общая на всю команду. Дальше всё упирается в тип связи в схеме:

| Что удаляем | Что происходит |
| ----------- | -------------- |
| Оффер, который ещё ведут связки | **409** и подсказка «деактивируйте»: `bundles.offerId` — RESTRICT, БД бы отказала сама, а диалог объясняет это человеческим языком |
| ГЕО или тег | Удаляются, связи снимаются каскадом join-таблицы; ответ несёт `unlinked`, и тост говорит «removed from N bundles», потому что это правка N чужих записей одним кликом |
| Аккаунт со связками | **409**: историю и треды каскад унёс бы вместе с логином; сначала переназначить или удалить связки |
| Аккаунт без связок | Удаляется, комментарии и записи истории уходят каскадом |

Плюс два правила, без которых CRM умеет закрыть сама себя: админ не может снять доступ с *себя*
и не может понизить или отключить *последнего* админа (`authorize()` не пускает отключённый
аккаунт, так что с одним-единственным админом это был бы конец работы). Отключение блокирует
следующий вход, но не активную сессию — JWT живёт до выхода, и экран говорит об этом прямо.

Каждая запись в справочник инвалидирует **оба** кэш-тега — `facets` (опции фильтров и формы) и
`dashboard` (в топ-5 на главной имена оффера и байера печатаются прямо из кэшированной
агрегации). Держать это в одном хелпере `lib/references.ts` нужно именно потому, что «переименовал
оффер — старое имя осталось в фильтре» не видно ни в одном коде, который это сломал.

## Импорт CSV

`POST /api/bundles/import` читает файл и отвечает построчно: что прошло, что нет и **почему**,
с номером строки так, как его показывает таблица. Диалог на `/bundles` («Import CSV») сначала
посылает файл как `dryRun` и показывает превью — «3 строки, 2 готовы, 1 с ошибкой» и список
проблем по полям, — и только потом пишет по настоящему. Один эндпоинт с флагом вместо двух,
чтобы превью не могло разойтись с тем, что импорт сделает.

- **Колонки = колонки экспорта.** Файл, скачанный в «Export CSV», правится и возвращается
  обратно. `CR %`, `ROI %` и `Profit` читаются и **игнорируются** (они считаются, а не
  вводятся), а `columns.ignored` в ответе честно перечисляет, что было опущено.
- **Справочники — не путь для импорта.** Неизвестный оффер или ГЕО валит строку с указанием
  вкладки Settings, которая это чинит. Разрешить таблице создавать офферы —
  значит позволить одному плохому файлу изобрести таксономию команды, а `payoutUSD` — число,
  которое строка CSV не знает.
- **Валидация та же схема, что и у формы.** `bundleSchema`, а не копия правил: «конверсий
  больше, чем кликов» ловится одним и тем же кодом и в форме, и в импорте. Схема запускается
  только после того, как справочники разрешены, — иначе несуществующий оффер отчитывался бы
  «Required» вместо внятной подсказки.
- **Один файл — одна транзакция.** Половина импортированной таблицы хуже отказа: естественная
  реакция на неполный список — импортнуть его ещё раз.
- **Права как при создании.** Байер импортирует на себя; колонка `Buyer` с чужим именем —
  ошибка строки, переназначение остаётся правом админа. Имя байера с совпадением у двух
  аккаунтов не угадывается: требуется email.
- **Лимиты:** 500 строк и 1 МБ на файл, 413 и 422 с внятным сообщением.
- Импортированная связка попадает в ленту как `import` («imported this bundle»), а не как
  созданная вручную: у загрузки файла есть своё слово в словаре `lib/timeline.ts`.

Быстрые действия с клавиатуры на `/bundles`: **N** — новая связка, **/** — фокус в поиск.
Молчат, пока курсор в поле ввода или открыта модалка (`hooks/useHotkeys.ts`).

## Уведомления

Колокольчик в хедере — ROI-алерты: связка, чья прибыль упала ниже порога из
Settings → Alerts. Порог вычитается из `settings`, сообщения лежат в `notifications`,
прочитанное — `readAt`.

- **Триггер — запись, а не расписание.** ROI — производное от `revenue` и `budgetSpent`,
  поэтому пересчитать его можно только там, где эти колонки только что изменились:
  `syncRoiAlerts` вызывается из `createBundle`, `updateBundle`, `finish()` (bulk и PATCH
  статуса) и из импорта. Планировщика в CRM нет, а правило, которое срабатывает по будильнику,
  сообщило бы о сливе через часы.
- **Получатели — владелец и все активные админы.** Дедупликация по непрочитанной паре
  (пользователь, связка): правка цифр не плодит десятую копию того же алерта.
- **Выздоровление снимает алерт.** Связка вернулась выше порога или ушла в архив —
  непрочитанное по ней удаляется; прочитанное не трогается: история колокольчика принадлежит
  читателю.
- **Порог меняют — колокольчик пересчитывается.** `PUT /api/settings` поднимает
  `recomputeRoiAlerts`: все непрочитанные алерты сбрасываются и поднимаются заново от новой
  линии. Иначе число в настройках и список в колокольчике расходились бы до тех пор, пока
  каждую связку снова не тронут, — а замечает это ровно тот админ, который порог и передвинул.
  Пересчёт живёт в роуте, а не в `writeSettings`, иначе `lib/references.ts` импортировал бы
  `lib/notifications.ts`, который уже импортирует оттуда `readSettings`.
- **Опрос, а не сокет** (60 с + возврат фокуса вкладки), и **без кэша**: алерт — то, что
  обязано быть показано в момент, когда связка пересекла черту.
- Неизвестный `type` рисуется колокольчиком: тип, добавленный позже, не исчезает из списка —
  тот же принцип, что у незнакомых ключей полей в ленте.

## Журнал изменений

`/audit` — та же история, что видна на странице связки, но прочитанная с другого конца: кто и
когда тронул что во всей системе. Источник — `BundleChange` и `Comment`, то есть журнал не
требует третьей записи «не забыть залогировать»: события уже и есть история.

- **Только админ** — и на странице, и на эндпоинте. Ссылка в навигации скрывается, но URL
  от этого не защищается: байер, открывший `/audit` прямой ссылкой, получает объяснение,
  а не чужую работу.
- **Две таблицы сливаются в один поток** с окном скана (500 записей из каждой) — как фильтр по
  производному ROI; за пределами окна `truncated` говорит об этом вслух вместо молча неверного
  итога.
- **Фильтр по полю исключает комментарии** — у комментария поля нет, поэтому `?field=…`
  не может вернуть строку, в которой нечего показать.
- **Слова те же, что в ленте** (`lib/timeline.ts`): одна запись не может прочитаться одним
  способом на связке и другим в журнале.
- Список полей фильтра берётся из самого журнала (`GROUP BY field`) и упорядочивается по
  словарю `timeline`, поэтому ключ, появившийся в более поздней версии, фильтруется в тот же
  день, когда впервые записан.
- **Не кэшируется**: журнал открывают, чтобы узнать, что произошло *только что*.

## Темы

Тёмная — по умолчанию (по ТЗ), светлая тоже полноценная, переключатель **System / Light / Dark**
в хедере. Реализация без `next-themes`:

- палитра живёт в семантических токенах (`bg-card`, `border-border`, `text-muted-foreground`,
  `text-success`, `text-destructive`, `--sidebar-*`), компоненты цвет не задают — иначе новая
  тема в них не подхватится;
- исключение намеренное: `lib/status.ts` держит оттенки статусов явно (цвет несёт смысл),
  но для каждого задана светлая и тёмная пара;
- выбор хранится в `localStorage`, а `lib/theme-storage.ts` встраивается в `<head>` инлайн-скриптом
  и ставит класс на `<html>` **до первой отрисовки** — мигания при загрузке нет;
- шрифт системный (SF Pro / Segoe UI Variable), веб-шрифтов нет — первый кадр не ждёт font-запрос;
- **цвета графиков задаются в JS** (`lib/chart-theme.ts` по `useResolvedTheme()`), потому что
  Recharts пишет их в SVG-атрибуты `fill`/`stroke`, куда `var(--token)` не подставляется.

Готовность проверяется скриншотами обеих тем на реальных страницах: смоук ходит в API, но
не видит рендер, а авторизованную страницу headless-браузер получает только через CDP
(`Network.setCookie` с сессией + `Page.captureScreenshot`).

## Кэш и мгновенная навигация

Под `cacheComponents` Next в дев-оверлее помечает **«uncached data during a navigation»** — это не
ошибка, а сигнал: переход по ссылке не может быть мгновенным, потому что страница ждёт
не-кэшированные данные. Против каждого случая — своё средство, а не «use cache везде»:

| Что | Почему так |
| --- | --- |
| Чтение сессии (`getSessionUser`) | `'use cache: private'` — значение живёт **только в браузере**, на сервер не пишется; именно это даёт Next prefetchить авторизованный шелл. Для route handler'ов есть отдельный `readSessionUser()` без приватного кэша — там записи держать некому |
| Справочники фильтров (`getBundleFacets`) | `use cache` + `cacheTag('facets')` + `cacheLife('minutes')`: меняются редко, а CRUD из `/settings` снимает тег каждой записью (`revalidateTag('facets', { expire: 0 })` в `lib/references.ts`) |
| Агрегаты дашборда (`getDashboardData`) | то же под тегом `dashboard`, и **любая** запись в `lib/bundles.ts` вызывает `revalidateTag('dashboard', { expire: 0 })` — иначе после массовой смены статусов цифры на главной остались бы старыми |
| `searchParams` страницы `/bundles` | на сервере не читается вообще: состоянием фильтра владеет клиент, а серверный `await` только блокировал навигацию |

Тонкость с `cacheLife`: пресет `'seconds'` даёт `stale = 1 s`, а при `stale < 30 s` Next исключает
scope из пререндеров и prefetch — кэш был бы, эффекта нет. Поэтому везде `'minutes'`.

Проверка: в `npm run smoke` есть кейс «cached dashboard is invalidated by a status change»
(8 → 9 → 8), а отсутствие инсайтов подтверждено реальным рендером — навигация `/ → /bundles → /`
в headless Edge через CDP (оверлей живёт в shadow DOM, его текст читается сквозь `shadowRoot`).

Один шум в логе остаётся и он не наш:

```
DeprecationWarning: Calling client.query() when the client is already executing a query
is deprecated and will be removed in pg@9.0.
```

Стек (`@prisma/client/runtime/client.js → interpretNode → performIO → pg/lib/client.js`) показывает,
что запросы вразнолад на одном соединении отправляет сам движок Prisma с pg-адаптером, а не код
приложения — там все вызовы последовательные. На корректность сегодня не влияет (Postgres
исполняет сообщения соединения по порядку), но на мажоре `pg@9` сломается, поэтому `pg`
закреплён на 8.x и при апгрейде это проверять первым. Попытка убрать его через интерактивную
`$transaction` не помогла — транзакция оставлена по другой причине: запись и её история теперь
фиксируются атомарно.

## Как устроена защита

Защита в несколько слоёв, и они не заменяют друг друга:

1. **`proxy.ts`** — только проверка *наличия* cookie сессии. Даёт честный HTTP-редирект
   на `/auth/login` для анонимных запросов. Под Partial Prerender сам `redirect()` внутри
   страницы не может вернуть 3xx: статический шелл (скелетон) уже отправлен, и редирект
   прилетает в потоке. Поэтому у анонимного `GET /` здесь 307, а не 200 со скелетоном.
   Правила «уже вошёл → убери со страницы входа» здесь намеренно **нет**: по одному лишь
   наличию cookie оно загоняло бы просроченный токен в цикл «/auth/login → / → /login».
2. **`lib/dal.ts`** — настоящая авторизация: `requirePageUser()` для страниц и
   `requireApiUser()` / `requireApiAdmin()` для каждого API-эндпоинта. Токен проверяется
   на подписи, поэтому фальшивая cookie показывает только скелетон без данных
   (это и проверяет смоук). Перед `auth()` стоит `await connection()`: без него Next
   ругается `blocking-prerender-crypto` на внутреннем редиректе Auth.js, и вместо
   перехода на форму входа пользователь получает упавший стрим.
3. **`next.config.ts → redirects()`** — `/login → /auth/login`. `auth()` из серверного
   компонента при отсутствии сессии редиректит на служебный `/login` и `pages.signIn`
   в этом пути не учитывает; вместо дубля страницы внутренний адрес мапится на реальную
   форму входа.

Правила прав: `ADMIN` видит и удаляет всё; `USER` создаёт свои связки и редактирует только
свои (`canManageBundle`). Регистрация всегда выдаёт роль `USER`.

## Откуда что берётся на дашборде

Числа на главной считаются по `BundleMetric` — дневным срезам, поэтому `date` в этой таблице
имеет тип `DATE` (`@db.Date`), а не timestamp: иначе каждая строка была бы «своим днём» и
группировка по дням была бы невозможна. Следствия, о которых легко забыть:

- итоги (`budgetSpent`, `revenue`, `clicks`, `conversions`) на самом `Bundle` остаются
  авторитетными для формы, а графики и «прибыль за месяц» читают дневные строки;
- Prisma отдаёт `DATE` как полночь по UTC, а машина в UTC+4 — поэтому подписи дней формируются
  из UTC-полей (`formatDayLabel`), а не через локальный `Intl`/`date-fns`;
- «Топ-5 по ROI за неделю» считается по тратам за 7 дней, а не по lifetime-итогам, и
  отфильтровывает связки с нулевой тратой (нет трат — нет доказательства ROI).

## Деплой на VPS (Docker)

Один `docker compose up` поднимает и базу, и приложение:

```bash
git clone https://github.com/Yaroslav164/Saints-crm.git && cd Saints-crm
AUTH_SECRET=$(openssl rand -base64 32) docker compose up -d --build
# http://localhost:3000   (свой порт: APP_PORT=8080 docker compose up -d)
```

Что происходит на старте контейнера (`docker/entrypoint.sh`):

| Шаг | Команда | Зачем |
| --- | ------- | ----- |
| 1 | проверка `DATABASE_URL` и `AUTH_SECRET` | без секрета сессии не подписываются — лучше упасть сразу, чем выпустить приложение, которое не пускает внутрь |
| 2 | `npx prisma migrate deploy` | схема нагоняется сама; образ носит миграции с собой, поэтому `docker run` без compose — тоже рабочая установка |
| 3 | `npm run db:seed`, если `SEED_ON_START=1` | только для демо: сид **перезаписывает** свои строки, поэтому по умолчанию выключен |
| 4 | `next start -H 0.0.0.0 -p $PORT` | прод-сервер Next |

| Переменная | По умолчанию | Назначение |
| ---------- | ------------ | ---------- |
| `AUTH_SECRET` | — (нужна) | подпись JWT-сессии |
| `APP_PORT` | `3000` | порт приложения на хосте |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | `postgres` / `postgres` / `saints_crm` | доступ и имя базы; `DATABASE_URL` собирается из них сам |
| `RUN_MIGRATIONS` | `1` | `0` — не трогать схему на старте |
| `SEED_ON_START` | `0` | `1` — залить демо-данные |
| `AUTH_URL` | не задана | нужна только если прокси переписывает `Host`; при `trustHost: true` обычный `proxy_pass` её не требует |

Порт PostgreSQL наружу **не публикуется**: на хосте и так обычно стоит свой Postgres на 5432,
а внутрь сети compose всегда есть чем залезть —
`docker compose exec db psql -U postgres -d saints_crm`.

Образ собран на `node:24-slim` в три стадии (deps → builder → runner) и сознательно **не** на
`output: "standalone"`: контейнер обязан уметь `prisma migrate deploy` и `db:seed`, то есть
нужны CLI, схема, `prisma7.config.ts`, `tsx` и сгенерированный клиент. Trade-off — размер
(~600 МБ против ~200 МБ): толстая картинка, которая сама создаёт свои таблицы, для внутренней
CRM полезнее тонкой, которой для этого нужен отдельный шаг. Работает под обычным `USER node`.

Пример прокси (nginx + certbot):

```nginx
server {
  listen 80;
  server_name crm.example.com;
  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;           # Auth.js строит callback из Host (trustHost)
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}
```

Обновление: `git pull && docker compose up -d --build` — миграции применит step 2.
Бэкап: `docker compose exec db pg_dump -U postgres saints_crm > backup.sql`.
Диагностика: `docker compose logs -f app` (у сервиса есть healthcheck на `/auth/login`).

Проверено на этой машине: `sh -n docker/entrypoint.sh` (POSIX-синтаксис) и то, что файл
хранится с LF (`.gitattributes`, иначе Windows-чекаут ломает контейнер строкой
`entrypoint.sh: not found`). Сам образ здесь не собирается — на этой машине нет Docker CLI,
так что `docker compose build` остаётся шагом на VPS.
